# 第 8 章：RAG 进阶与评估

> 状态：drafting

第 7 章我们跑通了最小 RAG：

```text
文档 -> 切分 -> 检索 -> 上下文 -> 回答 -> 引用
```

但 RAG 跑通不代表 RAG 可用。

真实项目里，RAG 经常会出现这些问题：

- 检索到了错误资料。
- 检索到了资料，但资料不足以回答。
- 资料是对的，模型却答偏了。
- 回答看起来对，但引用来源不支持结论。
- 资料库没有答案，系统却编造。

本章只做一件事：**把 RAG 的质量拆开评估**。

本章回答三个问题：

- 如何区分检索问题、回答问题和引用问题？
- 如何用一个小型固定测试集评估 RAG？
- 失败后应该调整文档、检索、Prompt，还是回答策略？

学完本章，你要留下三份项目资产：

- 一份 RAG 评估集：[rag-evaluation-set-template.md](./rag-evaluation-set-template.md)
- 一份失败分析表：[rag-failure-analysis-template.md](./rag-failure-analysis-template.md)
- 一个可运行评估示例：[rag_evaluation.py](../../examples/rag-evaluation/rag_evaluation.py)

## 不要只看最终回答

很多人评估 RAG 时只看一句：

```text
回答看起来对不对？
```

这不够。

RAG 至少要拆成三层看：

| 层次 | 要问的问题 |
| --- | --- |
| 检索质量 | 是否找到了正确资料？ |
| 回答质量 | 是否基于资料回答了问题？ |
| 引用质量 | 引用来源是否真的支持回答？ |

如果只看最终回答，你很难知道问题在哪里。

例子：

| 现象 | 可能原因 |
| --- | --- |
| 回答错了，检索片段也不相关 | 检索问题 |
| 检索片段正确，但回答仍然编造 | 生成或 Prompt 问题 |
| 回答正确，但引用了不支持结论的来源 | 引用策略问题 |
| 没有资料仍然回答得很自信 | 无答案处理问题 |

## 固定测试集是 RAG 调试的起点

不要每次随便问几个新问题。

先准备一组固定问题，每次改切分、检索参数或 Prompt 后，都用同一组问题重跑。

一个小型 RAG 评估集至少包含四类问题：

| 类型 | 示例 | 目的 |
| --- | --- | --- |
| 直接命中 | RAG 是让模型记住资料吗？ | 检查能否找到正确文档 |
| 概念区分 | 工作流和 Agent 的区别是什么？ | 检查能否命中关键解释 |
| 跨章节复用 | 结构化输出有什么用？ | 检查相近概念是否混淆 |
| 无答案问题 | 天气预报怎么查？ | 检查是否拒绝编造 |

第 8 章示例会用第 7 章的本地知识库跑一个固定评估集。

## 先评估检索

第一步先不要急着看模型回答。

先看检索结果：

```text
问题 -> 实际命中文档 -> 是否包含期望文档
```

比如：

| 问题 | 期望命中 | 检索是否通过 |
| --- | --- | --- |
| RAG 是让模型记住资料吗？ | `rag-basics.md` | 是 |
| 工作流和 Agent 的区别是什么？ | `ai-workflow.md` | 是 |
| 天气预报怎么查？ | 不应命中 | 是 |

如果检索不通过，先不要改 Prompt。

应该优先检查：

- 文档是否缺失。
- 切分是否太碎或太长。
- 检索关键词是否命中不了。
- `top_k` 是否太小或太大。
- 阈值是否过滤了正确片段，或放进了弱相关片段。

## 再评估回答

检索通过后，再看回答。

回答评估可以先用人工规则，不需要一开始就上复杂指标。

| 检查项 | 通过标准 |
| --- | --- |
| 是否基于资料 | 回答中的关键结论能在片段中找到依据 |
| 是否引用来源 | 至少标出来源文档或 chunk id |
| 是否处理资料不足 | 无答案问题不能硬答 |
| 是否符合用户任务 | 回答的是用户问题，不只是复述片段 |

第 8 章先建立这个习惯。

第 15 章会再讲更完整的 Agent Evaluation。

## 常见失败分类

RAG 失败时，先分类，再动手改。

| 失败类型 | 表现 | 优先处理 |
| --- | --- | --- |
| 文档缺失 | 知识库没有相关资料 | 补文档 |
| 切分问题 | 关键上下文被拆散 | 调整 chunk |
| 检索问题 | 命中错误片段或漏掉正确片段 | 调整检索方式、`top_k`、阈值 |
| 上下文问题 | 检索到了，但放进 Prompt 的片段太乱 | 改上下文组织 |
| 生成问题 | 资料正确，但模型回答跑偏 | 改 Prompt 或结构化输出要求 |
| 引用问题 | 引用不支持结论 | 改引用策略和校验 |
| 无答案问题 | 没资料也硬答 | 加拒答策略 |

这个分类比“RAG 效果不好”更有用。

## 成熟项目观察：mem0 和 Dify

### mem0：把“记住了什么”和“用对了什么”分开看

记忆系统和 RAG 很像，都容易出现一个问题：

```text
系统拿到了一些信息，但不代表它用对了。
```

观察 mem0 这类记忆系统时，本章只迁移一个思想：

```text
信息进入系统、被检索出来、被正确使用，是三个不同质量问题。
```

迁移到 AI 学习助手：

- 检索到课程资料，不等于回答正确。
- 回答引用了资料，不等于引用支持结论。
- 资料不足时拒答，也是质量的一部分。

### Dify：平台能搭流程，评估仍然要自己定义

Dify 这类平台可以快速搭建知识库问答流程。

但无论用平台还是手写代码，都要定义：

- 测试问题。
- 期望命中文档。
- 无答案问题。
- 引用检查。
- 失败分类。

平台能帮你跑流程，不能替你判断课程项目到底算不算答对。

## 项目锚点

AI 学习助手在本章要建立第一版知识问答评估集。

其他项目也可以这样做：

| 项目 | 评估重点 |
| --- | --- |
| 研究写作 Agent | 资料是否支持提纲和论点 |
| 客服工单 Agent | 是否命中正确 FAQ，是否错误引用规则 |
| 代码仓库助手 | 是否命中正确 README、目录和源码片段 |

每个项目都要准备“应该答”和“不应该答”的问题。

## 动手任务

完成下面 4 件事：

1. 填写 [rag-evaluation-set-template.md](./rag-evaluation-set-template.md)。
2. 运行 [rag_evaluation.py](../../examples/rag-evaluation/rag_evaluation.py)。
3. 记录失败原因到 [rag-failure-analysis-template.md](./rag-failure-analysis-template.md)。
4. 调整一次 `top_k` 或 `min_score`，比较前后结果。

运行示例：

```powershell
python .\examples\rag-evaluation\rag_evaluation.py
python .\examples\rag-evaluation\rag_evaluation.py --top-k 1
python .\examples\rag-evaluation\rag_evaluation.py --min-score 1
```

## 检查题

先自己判断，再看参考答案。

| 问题 | 你的判断 |
| --- | --- |
| RAG 回答错了，一定是模型问题吗？ |  |
| 为什么测试集要固定？ |  |
| 无答案问题为什么也要放进评估集？ |  |
| 检索命中了正确文档，是否等于最终回答正确？ |  |

参考答案：

| 问题 | 参考判断 |
| --- | --- |
| 不一定。可能是文档、切分、检索、上下文、生成或引用问题 |
| 固定测试集才能比较调整前后的效果 |
| 因为系统必须学会资料不足时拒答，不能编造 |
| 不等于。还要看模型是否正确使用资料并给出可靠引用 |

## 本章小结

这一章你把 RAG 从“能跑通”推进到“能评估”。

你现在应该已经有：

- 一组固定 RAG 测试问题。
- 每个问题的期望命中文档。
- 无答案测试样例。
- 一张失败原因分类表。
- 一次参数调整前后的对比记录。

下一章会开始加入工具调用，让模型不仅能读资料，还能在受控范围内调用外部能力。
