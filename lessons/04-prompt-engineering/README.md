# 第 4 章：Prompt Engineering 入门

> 状态：planned

## 本章定位

教读者把随意提问变成可控任务描述，让模型更稳定地完成指定工作。

## 承接上一章

上一章读者已经跑通模型调用，并看到了输出不稳定的问题。本章开始解决“如何把任务讲清楚”。

## 铺垫下一章

下一章会讲上下文工程和结构化输出。本章需要先建立 Prompt 的基本组成：角色、任务、约束、示例和输出要求。

## 学习目标

- 能把随意提示改写成结构化任务说明。
- 能区分角色、背景、任务、约束、示例和输出要求。
- 能用一组固定样例迭代 Prompt。

## 本章产出

- 一个 Prompt 版本对比记录。
- 一组 Prompt 测试样例。
- 一份 Prompt 常见问题清单。

## 学习任务

- 为自己的项目写出 v1 Prompt，明确角色、任务、约束和输出要求。
- 用第 2 章的 5 组样例测试 Prompt，记录失败案例。
- 迭代到 v2 Prompt，并说明改动解决了什么问题。

## 项目锚点

“AI 学习助手”在本章要把随意回答改成稳定的教学回答：解释概念、指出误区、给出下一步练习。客服工单 Agent 可以在本章完成分类 Prompt，研究写作 Agent 可以完成摘要和提纲 Prompt。

## 成熟项目讲解

- 主案例：OpenClaw。
- 讲解切口：个人助手如何把用户意图转成任务目标、约束和可执行步骤。
- 对应源码 Lab：[Lab 03：个人助手与数字分身](../../labs/03-personal-assistants/README.md)。
- 迁移到项目：把“AI 学习助手”的 Prompt 写成稳定教学任务，而不是临时聊天话术。

## 开源案例观察

观察 OpenClaw 这类个人助手项目如何把用户意图转成可执行任务。重点看“产品要服务用户目标”，不要把 Prompt 当成孤立技巧。

## 本章要写什么

- Prompt 的基本组成。
- 角色、任务、背景、约束和输出格式。
- Few-shot 示例什么时候有用。
- 如何从一次性 Prompt 迭代到可维护 Prompt。
- Prompt 常见错误。

## 本章不要写什么

- 不要把 Prompt 写成玄学技巧合集。
- 不要深入 JSON Schema 或解析。
- 不要展开 RAG 和 Agent。

## 小白易卡点

- 只复制“万能提示词”，不知道为什么有效。
- 把背景、任务和输出格式混在一起。
- 期待 Prompt 一次写好后永远稳定。

## 建议示例

把第 3 章的随意提示词改造成结构清晰的任务提示词，并比较输出差异。

## 建议图解

画一张 Prompt 组成图：任务、上下文、约束、示例、输出格式。
