# 第 7 章：RAG 基础

> 状态：drafting

第 6 章我们已经把 AI 学习助手做成了一个确定工作流。

现在要解决一个更现实的问题：

```text
如果答案必须依赖课程资料、笔记、FAQ 或代码文档，不能让模型只凭记忆回答。
```

这就是 RAG 要解决的问题。

RAG 的全称是 Retrieval-Augmented Generation，直译是“检索增强生成”。不要把它想复杂。第一版只记住这句话：

```text
先检索资料，再基于资料回答。
```

本章回答三个问题：

- RAG 和直接问模型有什么区别？
- 最小 RAG 流程由哪些步骤组成？
- 如何判断检索结果是否真的支持回答？

学完本章，你要留下三份项目资产：

- 一份 RAG 设计表：[rag-design-template.md](./rag-design-template.md)
- 一份检索测试表：[retrieval-test-template.md](./retrieval-test-template.md)
- 一个本地可运行示例：[local_rag.py](../../examples/local-rag/local_rag.py)

## 先看直接问模型的问题

假设用户问：

```text
第 6 章里工作流和 Agent 的区别是什么？
```

如果直接问模型，它可能会给一个通用答案。

但我们真正需要的是：

```text
根据本课程第 6 章的说法回答。
```

这时模型不能只靠训练时的知识。它需要先拿到课程资料，再基于资料回答。

RAG 把流程改成：

```text
用户问题
-> 检索相关资料
-> 把资料片段放进上下文
-> 生成带依据的回答
-> 返回引用来源
```

## RAG 不是让模型记住资料

这是初学者最常见的误解。

RAG 不是把文档塞给模型让它永久记住，也不是微调模型。

更准确地说：

| 做法 | 含义 |
| --- | --- |
| 直接问模型 | 模型根据已有参数和当前上下文回答 |
| RAG | 系统先找资料，再让模型基于资料回答 |
| 微调 | 改变模型参数，让模型学到新的模式或风格 |

RAG 的价值是：资料可以更新，回答可以引用来源，模型不用假装自己知道一切。

## 最小 RAG 的 5 个步骤

第一版先掌握 5 步。

| 步骤 | 做什么 | 本地示例怎么做 |
| --- | --- | --- |
| 准备文档 | 收集课程资料、FAQ、笔记 | `examples/local-rag/docs/` |
| 切分文档 | 把长文档切成小片段 | 按段落切分 |
| 检索片段 | 找和问题最相关的片段 | 用关键词重合做简单打分 |
| 组织上下文 | 把片段和来源放进回答上下文 | 保留文件名和 chunk id |
| 生成回答 | 只基于检索片段回答 | 示例用模板生成，后续可替换成 LLM |

本章不急着引入向量数据库。

先用最简单的本地检索看懂 RAG 链路，再在第 8 章讨论检索质量和评估。

## 文档为什么要切分

如果整篇文档都塞进上下文，会有几个问题：

- 太长，成本高。
- 噪声多，模型抓不住重点。
- 来源不精确，不知道答案来自哪一段。

切分的目标是：

```text
让每个片段足够短，能被检索；又足够完整，能支持回答。
```

第一版可以按段落切分。

后面再考虑标题层级、窗口重叠、语义切分和向量索引。

## 检索结果要能支撑回答

RAG 的关键不是“检索到了东西”，而是：

```text
检索到的片段是否足以回答问题？
```

看一个例子：

| 用户问题 | 好的检索结果 | 不好的检索结果 |
| --- | --- | --- |
| RAG 是让模型记住资料吗？ | 解释 RAG 是检索增强生成，不是永久记忆 | 只检索到 Prompt Engineering |
| 工作流和 Agent 有什么区别？ | 说明下一步由预设规则还是动态决策决定 | 只检索到 JSON 校验 |

如果检索结果不支持回答，系统应该说资料不足，而不是编造。

本章示例会在没有命中片段时返回：

```text
资料库没有找到足够依据，建议补充资料或换个问题。
```

## 把 RAG 接进第 6 章工作流

第 6 章的工作流是：

```text
question -> context -> structured output -> validation -> answer / clarification / error
```

加入 RAG 后变成：

```text
question
-> retrieve documents
-> build grounded context
-> generate answer with citations
-> validate answer and citations
-> answer / not enough evidence
```

注意，RAG 是工作流中的一组节点，不等于 Agent。

只要检索、生成、校验的步骤是提前写好的，它仍然是工作流。

## 成熟项目观察：Dify、OpenClaw 和代码仓库助手

本章主案例是 [Dify](https://github.com/langgenius/dify)，对比案例是 OpenClaw 和代码仓库助手类项目。

### Dify：把知识库变成流程节点

观察 Dify 时，不要只看“能拖拽知识库节点”。

要看它把 RAG 拆成了哪些工程问题：

- 文档怎么导入。
- 文档怎么切分。
- 查询时怎么检索。
- 检索结果怎么进入 Prompt。
- 回答如何保留来源。

迁移到 AI 学习助手：

```text
先用 3 到 5 篇课程资料跑通知识库问答，再讨论平台化。
```

### OpenClaw / 代码仓库助手：回答必须来自可访问资料

个人助手和代码仓库助手经常要回答“我的资料里有什么”“这个仓库怎么读”。

这类问题不能只让模型凭空回答。

它们需要：

- 读取可访问资料。
- 检索相关片段。
- 明确回答依据。
- 对资料不足的地方说“不确定”。

这也是本章 RAG 的底线。

## 项目锚点

AI 学习助手在本章加入课程资料检索。

其他项目也可以这样做：

| 项目 | 第一版知识库 |
| --- | --- |
| 研究写作 Agent | 研究资料、论文摘要、网页摘录 |
| 客服工单 Agent | FAQ、产品说明、退款规则 |
| 代码仓库助手 | README、docs、关键目录说明 |

每个项目都要先回答：

```text
用户问题必须依赖哪些外部资料？
```

先自己判断，再看参考答案。

| 问题 | 你的判断 |

| RAG 是不是让模型永久记住资料？ |  |
| 为什么要切分文档？ |  |

参考答案：

| 问题 | 参考判断 |
| --- | --- |
| 不是。RAG 是回答前检索资料，再基于资料生成 |
| 长文档成本高、噪声多，切分后更容易命中相关片段 |
| 来源能帮助用户检查依据，也方便后续评估 |
| 应该说明资料不足，避免编造 |

## 本章小结

这一章你跑通了最小 RAG 链路：

```text
文档 -> 切分 -> 检索 -> 上下文 -> 回答 -> 引用
```

你现在应该已经有：

- 一份 RAG 设计表。
- 一组本地知识库文档。
- 5 个检索测试问题。
- 对“资料不足不能硬答”的基本边界意识。
