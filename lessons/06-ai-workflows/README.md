# 第 6 章：AI 工作流

> 状态：planned

## 本章定位

教读者先用确定流程组织 AI 能力，理解很多任务不需要 Agent，也不应该一开始就做成 Agent。

## 承接上一章

上一章让模型输出变得可解析。本章把这些输出放进程序流程里，组成多步骤 AI 应用。

## 铺垫下一章

下一章会讲 RAG。本章需要先让读者理解：AI 能力通常是系统中的一个步骤，而不是全部系统。

## 学习目标

- 能区分 AI 工作流和 Agent。
- 能把模型调用、规则判断、人工确认和外部 API 组织成流程。
- 能设计失败处理、重试和降级策略。

## 本章产出

- 一张 AI 工作流流程图。
- 一个三步最小工作流示例。
- 一份“是否需要 Agent”的判断清单。

## 学习任务

- 把自己的项目拆成 3 到 5 个确定步骤，标出哪些步骤用模型，哪些步骤用普通代码。
- 画出工作流图，并标出失败重试和人工确认位置。
- 实现或伪代码描述一个最小工作流，不允许提前引入 Agent 自主循环。

## 项目锚点

“AI 学习助手”在本章形成固定流程：接收问题、结构化理解、生成回答、生成练习任务、记录结果。客服工单 Agent 可以形成分类、补全、查询、建议的处理流程。

## 成熟项目讲解

- 主案例：LangGraph。
- 对比案例：Dify、Flowise。
- 讲解切口：状态图和低代码节点如何表达一个可控 AI 工作流。
- 对应源码 Lab：[Lab 01：通用核心框架](../../labs/01-core-frameworks/README.md)、[Lab 07：低代码与无代码 Agent 平台](../../labs/07-low-code/README.md)。
- 迁移到项目：先把“AI 学习助手”做成可控工作流，再决定哪些步骤需要 Agent 化。

## 开源案例观察

观察 LangGraph 的状态图思路：很多 AI 应用先是可控工作流，再逐步变成 Agent。本章重点学习流程边界，不急着追求自主性。

## 本章要写什么

- Workflow 和 Agent 的区别。
- 多步骤 AI 应用的基本结构。
- 规则、模型、人工确认如何组合。
- 什么时候应该优先使用工作流。
- 工作流中的失败处理和重试。

## 本章不要写什么

- 不要提前讲 Agent 自主规划。
- 不要把工作流写成复杂编排平台教程。

## 小白易卡点

- 把所有多步骤流程都叫 Agent。
- 不知道哪些步骤应该用代码规则，哪些步骤才需要模型。
- 忽略失败重试和人工兜底。

## 建议示例

做一个三步流程：用户输入需求，模型结构化整理，程序根据字段生成下一步建议。
