# 第 5 章：上下文工程与结构化输出

> 状态：planned

## 本章定位

帮助读者理解上下文不是越多越好，模型输出也要尽量变成程序能处理的结构化结果。

## 承接上一章

上一章解决了如何写清楚 Prompt。本章进一步解决：Prompt 之外还要放什么上下文，以及如何让输出可解析。

## 铺垫下一章

下一章会讲 AI 工作流。本章需要让读者能把模型输出交给后续程序步骤处理。

## 学习目标

- 能判断哪些信息应该放入上下文。
- 能设计一个简单的结构化输出格式。
- 能处理输出格式不符合预期的情况。

## 本章产出

- 一个上下文组织示例。
- 一个结构化输出 Schema。
- 一段输出校验和失败重试逻辑。

## 学习任务

- 为项目设计一个结构化输出格式，明确字段名、字段含义和失败处理方式。
- 写一个最小校验逻辑，检查模型输出是否可被程序使用。
- 准备 2 个故意让模型输出不合规的样例，观察系统如何处理。

## 项目锚点

“AI 学习助手”在本章要输出结构化学习建议，例如概念解释、难点、练习任务和推荐资料。客服工单 Agent 可以输出分类、优先级和处理建议，研究写作 Agent 可以输出主题、论点、证据和引用占位。

## 成熟项目讲解

- 主案例：mem0、LangGraph。
- 讲解切口：mem0 讲什么信息值得沉淀为记忆，LangGraph 讲状态如何在流程中传递。
- 对应源码 Lab：[Lab 05：记忆、推理与模型服务专项](../../labs/05-memory-reasoning/README.md)、[Lab 01：通用核心框架](../../labs/01-core-frameworks/README.md)。
- 迁移到项目：把学习建议输出成可保存、可评估、可继续处理的结构化对象。

## 开源案例观察

观察 mem0 和 LangGraph：mem0 关注什么信息应该沉淀为记忆，LangGraph 关注状态如何在流程中流转。本章用它们帮助读者区分上下文、结构化输出和状态。

## 本章要写什么

- 什么是上下文工程。
- 如何选择放入上下文的信息。
- 如何避免上下文过长、过乱。
- 结构化输出的价值。
- JSON、Schema、字段校验和失败重试的基本思路。

## 本章不要写什么

- 不要深入向量检索。
- 不要提前讲完整评估系统。
- 不要把结构化输出写成某个 SDK 的参数说明。

## 小白易卡点

- 以为上下文越多越好。
- 以为要求输出 JSON 就一定能得到合法 JSON。
- 不知道模型输出失败后应该重试、修复还是人工处理。

## 建议示例

让模型把一段用户需求整理成固定字段，例如目标、输入、输出、限制和风险。
