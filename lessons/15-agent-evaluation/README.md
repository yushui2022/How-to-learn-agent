# 第 15 章：Agent Evaluation 评估方法

> 状态：planned

## 本章定位

教读者判断一个 AI 应用或 Agent 是否真的变好了，而不是只凭感觉看几个输出。

## 承接上一章

前面已经讲了 RAG、工具、Agent loop、Planning、Memory 和 Multi-Agent。本章开始回答：这些系统如何评估。

## 铺垫下一章

下一章会讲观测和调试。评估告诉我们有没有问题，观测和调试帮助我们找到问题在哪里。

## 学习目标

- 能设计一组固定任务来评估 AI 应用或 Agent。
- 能区分最终输出评估、过程评估和工具调用评估。
- 能理解 LLM-as-judge 的适用范围和风险。

## 本章产出

- 一组 Agent 回归测试任务。
- 一张失败类型分类表。
- 一份评估记录模板。

## 学习任务

- 为项目准备至少 10 个固定测试任务。
- 记录每个任务的最终输出、关键执行步骤、工具调用和失败原因。
- 设计一个简单评分表，区分任务成功、部分成功和失败。

## 项目锚点

“AI 学习助手”在本章要建立学习建议质量评估集。研究写作 Agent 要评估资料覆盖、引用准确性和文章结构，客服工单 Agent 要评估分类准确率和处理建议可用性。

## 成熟项目讲解

- 主案例：mem0。
- 对比案例：AutoGen、LiteLLM、OpenHands。
- 讲解切口：记忆质量、任务成功率、工具调用正确性、成本和回归测试。
- 对应源码 Lab：[Lab 05：记忆、推理与模型服务专项](../../labs/05-memory-reasoning/README.md)、[Lab 04：多智能体协作](../../labs/04-multi-agent/README.md)、[Lab 02：编程 Agent](../../labs/02-coding-agents/README.md)。
- 迁移到项目：为“AI 学习助手”建立最小评估集，并记录过程指标而不只看最终回答。

## 开源案例观察

观察 mem0 的记忆评估、AutoGen 的多 Agent 任务结果，以及 LiteLLM 的调用成本记录。评估应该覆盖质量、过程、工具调用和成本，而不是只看最终输出。

## 本章要写什么

- 为什么 AI 项目不能只靠传统单元测试。
- 样例集和回归测试。
- 任务成功率、质量评分和失败分类。
- LLM-as-judge 的适用范围和风险。
- RAG、Tool Calling、Agent 轨迹的不同评估点。

## 本章不要写什么

- 不要把评估写成只看主观感觉。
- 不要过早引入复杂评测平台。
- 不要忽略人工评审的价值。

## 小白易卡点

- 只看最终回答，不看执行过程。
- 把 LLM-as-judge 当成绝对客观评分。
- 没有固定测试集，导致每次优化都无法比较。

## 建议示例

为前面的小 Agent 准备一组固定任务，记录每次执行是否成功、失败在哪里。

## 建议图解

画一张评估链路图：测试样例、执行轨迹、输出、评分、失败分析。
