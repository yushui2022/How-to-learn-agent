# 第 2 章：从想法到 AI 原型

> 状态：drafting

上一章我们学会了判断一个需求属于哪类 AI 项目：普通程序、单次 LLM 调用、结构化 LLM 应用、RAG、工作流、工具调用，还是 Agent。

这一章继续往前走：**把一个听起来很大的想法，压成第一版可以验证的 AI 原型**。

本章回答三个问题：

- 一个模糊想法，怎样拆成用户、场景、输入、输出和约束？
- 第一版原型应该做到什么程度，哪些能力应该延后？
- 下一章写第一次 LLM 调用前，必须准备哪些样例和验收标准？

学完本章，你要留下两份项目资产：

- [AI 原型一页纸](./prototype-one-pager-template.md)
- [输入输出样例表](./io-samples-template.md)

## 先看一个场景

我们要做贯穿项目：

```text
AI 学习助手
```

很多人第一反应会写成这样：

```text
做一个 AI 学习助手，可以根据用户目标自动规划路线，搜索资料，讲解知识点，出题，批改，记住学习进度，并持续督促用户复习。
```

这个描述不是错，而是太大。

如果直接拿它开工，你很快会遇到几个问题：

- 不知道第一天应该写哪段代码。
- 不知道模型输入和输出长什么样。
- 不知道怎样判断效果好坏。
- 不知道哪些功能现在必须做，哪些只是未来方向。

原型的作用，就是先把它压成一个可验证的小任务：

```text
用户输入一个 AI Agent 学习问题，系统返回三个字段：
1. 简洁解释
2. 常见误区
3. 下一步练习
```

这就是第一版 AI 学习助手的原型。

它还不需要登录、记忆、知识库、工具调用、自动规划、多 Agent 协作。它只验证一件事：

```text
模型能不能把一个学习问题稳定地变成有教学价值的结构化回答？
```

## 原型不是产品缩小版

原型不是把完整产品每个功能都做一点。

更好的做法是：**只保留一条最关键的用户路径，把它做完整**。

对 AI 学习助手来说，第一版用户路径可以是：

```text
输入问题 -> 生成结构化回答 -> 人工判断回答是否有用
```

这条路径足够短，但它已经能验证三个关键问题：

| 要验证的问题 | 为什么重要 |
| --- | --- |
| 模型是否理解学习问题 | 如果问题都理解错，后面接 RAG 或 Agent 也救不了 |
| 回答是否有固定结构 | 下一章才容易写 Prompt，后续也容易接前端或评估 |
| 输出是否真的帮助学习 | AI 项目不能只看“像不像回答”，还要看用户任务是否完成 |

一个好的原型通常满足四个条件：

- 输入明确。
- 输出明确。
- 约束明确。
- 成功标准明确。

## 第一步：写清用户和场景

不要先写功能列表，先写一句用户场景。

格式可以很简单：

```text
当【某类用户】在【某个场景】遇到【某个问题】时，
他希望系统帮他完成【一个具体任务】。
```

AI 学习助手可以这样写：

```text
当正在学习 AI Agent 的中文初学者遇到一个概念问题时，
他希望系统用简洁语言解释概念，指出常见误区，并给出一个下一步练习。
```

注意这里没有写“自动规划完整路线”，也没有写“长期记住学习进度”。因为这些不是第一版必须验证的事情。

再看三个可选项目的写法：

| 项目 | 第一版用户场景 |
| --- | --- |
| 研究写作 Agent | 当用户准备研究一个主题时，系统先帮他把主题拆成 5 个可搜索的问题 |
| 客服工单 Agent | 当客服收到一条工单时，系统先判断问题类型、紧急程度和建议处理人 |
| 代码仓库助手 | 当开发者刚进入一个仓库时，系统先根据 README 和目录结构解释项目用途 |

每个场景都只保留一个最小任务。

## 第二步：定义输入和输出

AI 原型最容易失控的地方，是只写“让 AI 回答一下”，却没有规定输入和输出。

第一版至少写清楚两类输入：

| 输入类型 | 说明 | AI 学习助手示例 |
| --- | --- | --- |
| 用户输入 | 用户直接给系统的内容 | 什么是 ReAct？ |
| 系统约束 | 系统提前规定的回答要求 | 面向初学者；不超过 300 字；必须包含练习 |

输出也要写成固定结构。

AI 学习助手第一版可以规定为：

```json
{
  "explanation": "用初学者能理解的话解释概念",
  "misconception": "指出一个常见误区",
  "exercise": "给一个 10 分钟内能完成的小练习"
}
```

这一步很关键。因为下一章第一次调用 LLM 时，我们不是随便问模型，而是要让模型尽量稳定地生成这个结构。

## 第三步：给原型画边界

边界不是偷懒，而是让第一版能完成。

可以把能力分成三栏：

| 分类 | 含义 | AI 学习助手示例 |
| --- | --- | --- |
| 第一版必须有 | 没有它就无法验证核心任务 | 对学习问题生成结构化回答 |
| 第一版暂不覆盖 | 重要，但不是第一版必须验证 | 记住用户学习进度、引用课程资料 |
| 后续可能加入 | 等第一版验证后再做 | RAG、工具调用、长期记忆、学习计划 Agent |

用这个方法拆一下：

| 能力 | 第一版要不要做 | 判断 |
| --- | --- | --- |
| 概念解释 | 要 | 这是核心任务 |
| 常见误区 | 要 | 能体现教学价值 |
| 下一步练习 | 要 | 能推动用户继续学习 |
| 搜索资料 | 暂不做 | 第 7 章 RAG 再处理 |
| 记住进度 | 暂不做 | 第 13 章 Memory 再处理 |
| 自动规划学习路线 | 暂不做 | 第 12 章 Planning 再处理 |
| 调用外部工具 | 暂不做 | 第 9 章 Tool Calling 再处理 |

第一版边界越清楚，后面的代码越容易写。

## 第四步：写验收标准

验收标准回答：

```text
什么结果算可用？什么结果算失败？
```

不要只写“回答质量好”。这太模糊。

AI 学习助手第一版可以这样写：

| 类型 | 标准 |
| --- | --- |
| 格式 | 输出必须包含解释、误区、练习三个部分 |
| 内容 | 解释面向初学者，不使用一堆未解释的术语 |
| 任务 | 练习必须能在 10 分钟内完成 |
| 边界 | 不编造课程资料来源，不假装读取了外部文档 |
| 失败 | 如果问题太模糊，应先给出澄清问题，而不是硬答 |

这张表下一章会直接变成测试样例和人工检查标准。

## 输入输出样例先于代码

在写代码前，先准备 5 组样例。

样例不是为了“喂给模型背答案”，而是为了让你知道自己到底想要什么。

| 编号 | 用户输入 | 期望输出重点 |
| --- | --- | --- |
| 1 | 什么是 RAG？ | 解释“先检索资料，再基于资料回答”，指出不是让模型背知识 |
| 2 | Agent 和工作流有什么区别？ | 说明关键差别是下一步是否动态决策 |
| 3 | ReAct 是什么？ | 解释推理和行动交替，给一个观察-思考-行动小练习 |
| 4 | 我总是把 Prompt 写很长怎么办？ | 指出常见误区：把需求、约束、示例混在一起 |
| 5 | 帮我学会所有 AI Agent | 先澄清目标和时间，不直接生成庞大学习计划 |

第 5 条很重要。真实用户经常给出过大的请求，原型必须知道什么时候应该澄清，而不是盲目回答。

## 成熟项目观察：从 OpenClaw 和 mem0 反推 MVP

本章不做源码逐行阅读，只做一个训练：**看到成熟项目时，反推出它的最小起点**。

对应源码 Lab：

- [Lab 03：个人助手与数字分身](../../labs/03-personal-assistants/README.md)
- [Lab 05：记忆、推理与模型服务专项](../../labs/05-memory-reasoning/README.md)

### 观察 OpenClaw：完整个人助手不是第一版目标

[OpenClaw](https://github.com/openclaw/openclaw) 适合当作产品型个人助手案例来观察。

看这类项目时，不要一上来就照搬所有能力。先问四个问题：

| 观察点 | 要问的问题 | 对第二章的启发 |
| --- | --- | --- |
| 入口 | 用户从哪里发起任务？ | 第一版可以只有一个命令行或网页输入框 |
| 任务 | 用户最常让助手完成什么？ | 第一版只保留一个高频任务 |
| 工具 | 哪些动作需要调用外部工具？ | 第一版可以先不接工具，避免范围爆炸 |
| 记忆 | 哪些信息需要长期保存？ | 第一版先不用记忆，等核心回答稳定后再加 |

如果从 OpenClaw 反推一个个人助手 MVP，它可能不是“全渠道、全工具、全记忆”的大系统，而是：

```text
一个入口 + 一个任务 + 一种输出 + 一组安全边界
```

把这个思路迁移到 AI 学习助手：

```text
一个入口：用户输入学习问题
一个任务：生成结构化教学回答
一种输出：解释、误区、练习
一组边界：不假装读取资料，不处理过大的学习目标
```

### 观察 mem0：记忆是能力，不是第一版全部

[mem0](https://github.com/mem0ai/mem0) 适合当作记忆基础设施案例来观察。

它提醒我们：长期记忆不是“把所有聊天记录塞回上下文”。一个记忆系统至少要考虑：

- 什么信息值得保存。
- 保存后什么时候检索。
- 旧记忆怎么更新。
- 用户怎样查看或删除。

但在第二章，我们要做的判断是：

```text
AI 学习助手第一版是否必须有长期记忆？
```

答案通常是：不必须。

第一版先验证“单次学习问题能否被解释清楚”。等这个能力稳定后，再进入第 13 章，把学习目标、已学章节、薄弱点做成可控记忆。

成熟项目的价值不是让你一开始做得一样复杂，而是帮助你判断：

```text
哪些能力现在必须做，哪些能力应该等到合适章节再做。
```

先自己判断，再看参考答案。

| 问题 | 你的判断 |
| --- | --- |
| “帮我做一个全自动学习 Agent”能不能直接作为第一版需求？ |  |
| 为什么第二章要求先写输入输出样例，再写代码？ |  |
| AI 学习助手第一版为什么不需要长期记忆？ |  |
| 如果用户输入“帮我学会所有 AI”，第一版应该直接回答还是先澄清？ |  |

参考答案：

| 问题 | 参考判断 |
| --- | --- |
| 不能。它范围太大，缺少明确输入、输出、边界和验收标准 |
| 样例能提前暴露需求模糊、输出不稳定和验收标准缺失的问题 |
| 第一版只验证单次学习问题的结构化回答，记忆属于后续能力 |
| 应该先澄清目标、基础、时间和学习范围 |

## 本章小结

这一章我们把“做一个 AI 学习助手”压成了第一版原型：

```text
用户输入学习问题 -> 系统输出解释、误区、练习
```

你现在应该已经有：

- 一个清楚的用户场景。
- 一个最小任务。
- 一组输入输出样例。
- 一份验收标准。
- 一条明确的第一版边界。

下一章我们会基于这些内容，真正发起第一次 LLM 调用。
