# 第 16 章：Observability 观测与调试

> 状态：planned

## 本章定位

教读者记录和分析一次 AI 或 Agent 执行过程，知道问题发生在模型、Prompt、检索、工具还是状态管理。

## 承接上一章

上一章讲了如何评估好坏。本章继续讲发现问题后如何定位原因。

## 铺垫下一章

下一章会讲安全和可信。只有看得见执行过程，才能审计越权调用、异常输入和不可靠行为。

## 学习目标

- 能设计一次 Agent 执行过程的 trace 记录。
- 能从日志中定位 Prompt、检索、工具调用或状态管理问题。
- 能复现一次失败并给出可操作的修复方向。

## 本章产出

- 一份 Agent trace 样例。
- 一张执行时间线图。
- 一份调试检查清单。

## 学习任务

- 为项目设计一次完整执行 trace，包含输入、Prompt、检索、工具、状态和输出。
- 选择一个失败案例，沿 trace 找到失败发生在哪一步。
- 写一份调试复盘，说明下一次要改 Prompt、检索、工具还是状态管理。

## 项目锚点

“AI 学习助手”在本章要能追踪一次学习建议生成过程。代码仓库助手要特别记录文件检索、工具调用和测试结果，方便判断建议是否可靠。

## 成熟项目讲解

- 主案例：LangGraph、LiteLLM。
- 对比案例：OpenClaw、OpenHands。
- 讲解切口：模型调用、工具调用、状态变化、错误、成本和 trace 的记录方式。
- 对应源码 Lab：[Lab 01：通用核心框架](../../labs/01-core-frameworks/README.md)、[Lab 02：编程 Agent](../../labs/02-coding-agents/README.md)、[Lab 05：记忆、推理与模型服务专项](../../labs/05-memory-reasoning/README.md)。
- 迁移到项目：为“AI 学习助手”保存一次完整执行轨迹，能从 trace 反推失败原因。

## 开源案例观察

观察 LangGraph、LiteLLM 和 OpenClaw：真实系统需要记录模型调用、工具调用、状态变化、错误和成本。读者要学会从 trace 反推失败原因。

## 本章要写什么

- AI 应用需要记录哪些日志。
- Trace 的基本概念。
- Prompt、模型输出、检索结果、工具调用和错误信息如何关联。
- 如何复现一次失败。
- 如何用日志支持评估和迭代。

## 本章不要写什么

- 不要把内容写成某个观测平台广告。
- 不要记录敏感信息而不说明风险。
- 不要只讲后端日志，忽略 Agent 执行轨迹。

## 小白易卡点

- 只记录最终输出，不记录中间输入和工具结果。
- 日志里混入敏感信息。
- 失败不可复现，导致只能凭感觉改 Prompt。
