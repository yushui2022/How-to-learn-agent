# 第 10 章：Agent 到底是什么

> 状态：drafting

第 9 章我们已经把模型接到了工具上：

```text
模型提出工具请求 -> 程序校验 -> 程序执行 -> 记录日志
```

这时最容易出现一个误解：

```text
能调用工具 = Agent
```

这个判断太粗了。

一个能查资料、生成练习、保存记录的系统，可能只是一个工具调用应用。只有当系统能够围绕目标，在状态和反馈的影响下自己选择下一步，并且可以重复行动时，它才开始接近 Agent。

本章只解决一个问题：

```text
什么时候一个 AI 应用值得升级成 Agent？
```

本章回答三个问题：

- Agent 和 Chatbot、Workflow、RAG、Tool Calling 有什么区别？
- 一个最小 Agent 至少包含哪些工程组件？
- 如何判断“AI 学习助手”现在该不该 Agent 化？

学完本章，你要留下三份项目资产：

- 一份 Agent 判断清单：[agent-decision-checklist-template.md](./agent-decision-checklist-template.md)
- 一份 Agent 范围卡：[agent-scope-card-template.md](./agent-scope-card-template.md)
- 一个本地判断示例：[agent_decision.py](../../examples/agent-decision/agent_decision.py)

## 先给一个工程定义

在这门课里，我们先用下面这个定义：

```text
Agent 是一个围绕目标运行的软件系统。
它会维护状态，观察反馈，在多个可能动作中选择下一步，
调用工具或模型执行动作，并在完成、失败或触发边界时停止。
```

这个定义里有 6 个关键词：

| 关键词 | 含义 |
| --- | --- |
| 目标 | 系统要完成什么任务，而不是只回答一句话 |
| 状态 | 当前任务进展、上下文、历史结果和约束 |
| 观察 | 工具返回、用户反馈、错误信息、环境变化 |
| 选择 | 下一步不是完全固定的，系统要根据观察做判断 |
| 行动 | 调用模型、工具、检索、写入记录或请求用户确认 |
| 停止 | 有完成条件、失败条件、最大步数和人工接管规则 |

如果一个系统没有状态、没有选择、没有循环，通常不要急着叫它 Agent。

## 能力阶梯

可以把前面几章学过的能力放到一条阶梯上：

```text
LLM 调用
-> Prompt 和上下文控制
-> 结构化输出
-> 固定工作流
-> RAG
-> Tool Calling
-> Agent
```

它们不是互相替代的关系，而是逐步增加能力和风险。

| 类型 | 系统做什么 | 下一步由谁决定 |
| --- | --- | --- |
| LLM 调用 | 根据输入生成一段回答 | 开发者或用户 |
| 固定工作流 | 按预设步骤执行 | 开发者提前写死 |
| RAG 应用 | 检索资料后回答 | 流程固定，资料动态 |
| Tool Calling 应用 | 模型请求工具，程序执行 | 工具由模型请求，但流程常常仍固定 |
| Agent | 根据目标、状态和反馈持续选择动作 | 系统在边界内动态决定 |

判断一个系统是不是 Agent，不要看名字。

要看它是否有动态决策、状态更新、反馈循环和停止条件。

## 用同一个任务做对比

假设用户说：

```text
我想两周内学会 RAG，帮我安排学习。
```

不同系统会这样处理。

### 普通 Chatbot

它直接生成一份学习建议：

```text
第 1 天了解 RAG，第二天学习向量检索……
```

这不是 Agent。它没有检查资料、没有跟踪进度，也不会根据后续结果调整。

### 固定工作流

工作流可以提前写好步骤：

```text
收集目标 -> 生成计划 -> 生成练习 -> 输出结果
```

如果每次都按同样顺序执行，它仍然不是 Agent。它是可控、稳定、容易测试的 AI 工作流。

很多项目应该先从工作流开始。

### RAG 应用

RAG 会先检索课程资料，再基于资料生成计划：

```text
检索 RAG 章节 -> 读取相关片段 -> 生成学习计划并引用来源
```

这也不一定是 Agent。它解决的是“资料从哪里来”的问题，不是“下一步谁来决定”的问题。

### Tool Calling 应用

工具调用应用可以让模型请求工具：

```text
search_course_notes("RAG")
generate_practice("RAG")
save_learning_record(...)
```

这仍然不自动等于 Agent。它只是具备了行动能力。

如果程序只允许它在固定流程里调用固定工具，它更像一个带工具的工作流。

### Agent

Agent 会围绕目标循环推进：

```text
观察：用户目标是两周学会 RAG
思考：先检查现有基础
行动：查询用户已学章节
观察：用户还没完成第 7 章
思考：先补 RAG 基础，不直接进入评估
行动：生成第 7 章复习任务
观察：用户完成练习但错在“无答案处理”
思考：安排第 8 章评估练习
行动：生成新的练习并保存进度
停止：达到当天学习目标，等待用户反馈
```

这里的关键不是“步骤多”，而是：

- 下一步会根据观察结果变化。
- 系统会维护任务状态。
- 工具结果会影响后续决策。
- 系统知道什么时候停止或请求用户。

## 最小 Agent 的 6 个组件

进入 Agent 阶段前，先确认这 6 个组件是否存在。

| 组件 | 要回答的问题 | AI 学习助手示例 |
| --- | --- | --- |
| Goal | 这次要完成什么目标？ | 两周内学会 RAG |
| State | 当前任务进展是什么？ | 已学章节、练习结果、薄弱点 |
| Tools | 可以调用哪些外部能力？ | 查资料、生成练习、保存记录 |
| Policy | 什么时候选哪个动作？ | 没学基础先复习，错题多就加练习 |
| Feedback | 如何知道动作是否有效？ | 用户答案、工具返回、评估结果 |
| Boundary | 哪些动作禁止自动执行？ | 删除记录、发消息、提交外部表单 |

如果这些问题答不出来，先不要写 Agent loop。

先回到工作流、RAG 或工具调用，把边界补清楚。

## 自主性不是越高越好

Agent 的“自主”不是一个开关，而是一组可控权限。

| 自主维度 | 低自主 | 高自主 | 初学项目建议 |
| --- | --- | --- | --- |
| 选择下一步 | 固定流程 | 动态选择任务路径 | 允许动态选择学习任务 |
| 调用工具 | 只能调用只读工具 | 可调用写入和外部动作 | 先开放只读工具 |
| 迭代次数 | 单步或两步 | 多轮循环直到完成 | 设置最大步数 |
| 记忆写入 | 用户确认后写入 | 自动更新长期记忆 | 先让用户确认 |
| 外部联系 | 不发送消息 | 自动发邮件、提交表单 | 初期禁止 |

真正的工程能力不是把 Agent 放得越自由越好，而是知道哪些自主性现在可以开放，哪些必须限制。

## 成熟项目观察：OpenClaw、LangGraph 和 SmolAgents

本章的成熟项目观察不做源码逐行讲解，只看三种不同层次：

- [OpenClaw](https://github.com/openclaw/openclaw)：从产品角度看个人 Agent 如何组织会话、技能和用户目标。
- [LangGraph](https://github.com/langchain-ai/langgraph)：从框架角度看如何用状态和图控制 Agent 执行。
- [SmolAgents](https://github.com/huggingface/smolagents)：从轻量实现角度看 Agent 的最小形态。

对应源码 Lab：

- [Lab 01：通用核心框架](../../labs/01-core-frameworks/README.md)
- [Lab 03：个人助手与数字分身](../../labs/03-personal-assistants/README.md)
- [Lab 08：轻量入门与研究级 Agent](../../labs/08-lightweight-research/README.md)

### OpenClaw：先看产品边界

观察个人助手类项目时，不要先问“它有多少功能”。

先问：

- 用户入口在哪里？
- 用户目标如何进入系统？
- 会话状态如何保留？
- 技能或工具如何被组织？
- 哪些动作需要权限边界？

迁移到 AI 学习助手：

```text
把学习助手看成一个产品，而不是一个 Prompt。
先定义它能帮用户完成哪些学习目标，再定义它可以调用哪些工具。
```

### LangGraph：先看状态和控制

框架型项目的价值不只是“帮你写 Agent”。

更重要的是它提醒你：

```text
Agent 需要被控制。
```

用状态、节点、边、条件和持久化把执行过程显式化，比让模型在一个巨大 Prompt 里自由发挥更容易调试。

迁移到 AI 学习助手：

```text
先把状态对象写清楚：用户目标、当前章节、练习结果、下一步候选动作。
```

第 11 章再把这个状态放进执行循环。

### SmolAgents：先看最小结构

轻量项目适合初学者观察 Agent 的最小骨架：

- 工具列表。
- 模型输出。
- 执行动作。
- 返回观察。
- 决定是否继续。

迁移到 AI 学习助手：

```text
先实现一个能看清每一步的最小 Agent，不要一开始就复制大型框架。
```

## 项目锚点

AI 学习助手到目前已经具备这些能力：

| 已学章节 | 能力 |
| --- | --- |
| 第 3 章 | 能调用模型 |
| 第 4 章 | 能控制 Prompt |
| 第 5 章 | 能输出结构化结果 |
| 第 6 章 | 能放进固定工作流 |
| 第 7-8 章 | 能检索和评估资料 |
| 第 9 章 | 能定义和调用工具 |

现在要判断它是否需要升级成 Agent。

可以用下面的判断：

| 需求 | 推荐形态 |
| --- | --- |
| 用户问一个概念，系统解释清楚 | Chatbot 或 RAG |
| 用户上传资料，系统按固定流程生成总结 | Workflow |
| 用户问课程内容，系统检索资料后回答 | RAG 应用 |
| 用户要求生成练习并保存学习记录 | Tool Calling 应用 |
| 用户给出长期目标，系统要跟踪进度、选择任务、根据结果调整 | Agent 候选 |

本章不是要求你立刻写完整 Agent，而是要求你做出清楚判断：

```text
这个需求是否真的需要动态决策和反馈循环？
```

- 为什么某些需求用工作流或 RAG 更合适？
- 为什么某些需求虽然像 Agent，但必须限制工具、步数和副作用？

## 检查题

先自己判断，再看参考答案。

| 问题 | 你的判断 |
| --- | --- |
| Tool Calling 是否等于 Agent？ |  |
| 一个固定工作流里用了模型，是否一定是 Agent？ |  |
| Agent 至少需要哪些工程组件？ |  |
| 为什么 Agent 必须有停止条件？ |  |
| AI 学习助手什么时候才值得 Agent 化？ |  |

参考答案：

| 问题 | 参考判断 |
| --- | --- |
| 不等于。Tool Calling 只是让模型请求外部能力，Agent 还需要目标、状态、反馈循环和动态决策 |
| 不一定。步骤由开发者提前固定时，它更像工作流 |
| 至少需要目标、状态、工具、决策策略、反馈和边界 |
| 没有停止条件，系统可能无限循环、反复调用工具、增加成本或执行错误动作 |
| 当它要围绕长期学习目标跟踪进度、选择下一步、根据结果调整任务时，才值得 Agent 化 |

## 本章小结

这一章你应该建立一个清晰判断：

```text
Agent 不是“用了大模型”的系统，
也不是“能调用工具”的系统，
而是能在边界内围绕目标持续决策和行动的系统。
```

你现在应该已经有：

- 一份是否需要 Agent 的判断清单。
- 一份 Agent 范围卡。
- 一个对 AI 学习助手当前形态的判断。
- 一组必须限制的自主动作。

下一章会在这个判断基础上，真正写出最小 Agent 执行循环。
