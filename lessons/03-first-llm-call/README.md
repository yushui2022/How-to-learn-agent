# 第 3 章：第一次 LLM 调用

> 状态：planned

## 本章定位

让读者真正跑通第一次模型调用，并理解 LLM 调用的基本输入、输出、成本和不确定性。

## 承接上一章

上一章已经把想法拆成了明确任务。本章用这个任务作为第一次模型调用的目标。

## 铺垫下一章

下一章会讲 Prompt Engineering。本章需要先让读者看到：同一个任务，如果只随便写一句话，输出会不稳定。

## 学习目标

- 能跑通一次最小 LLM 调用。
- 能理解消息、上下文、token、温度、延迟和成本的直观含义。
- 能保存一次调用的输入、输出和错误信息。

## 本章产出

- 一个最小可运行脚本。
- 一份模型调用记录。
- 一组不同参数下的输出对比。

## 学习任务

- 用第 2 章的输入输出样例跑通第一次模型调用。
- 保存至少 3 次调用记录，观察同一输入的输出差异。
- 调整一个模型参数，记录它对输出长度、稳定性或风格的影响。

## 项目锚点

“AI 学习助手”在本章完成第一个可运行版本：给定学习问题，模型返回回答。其他项目也只做最小调用，不引入 RAG、工具或 Agent。

## 成熟项目讲解

- 主案例：LiteLLM。
- 讲解切口：真实项目为什么需要模型网关、统一调用接口、失败处理、成本记录和模型切换。
- 对应源码 Lab：[Lab 05：记忆、推理与模型服务专项](../../labs/05-memory-reasoning/README.md)。本章只读模型网关的定位和统一接口，不要求深入生产部署。
- 迁移到项目：先保留最小 LLM 调用接口，为后续切换模型、记录日志和控制成本留下位置。

## 开源案例观察

观察 LiteLLM 这类模型网关项目为什么存在：真实项目不会只写一次裸模型调用，还需要模型切换、日志、成本和失败处理。本章只建立直觉，不展开生产化。

## 本章要写什么

- 一次 LLM 调用的基本结构。
- 模型输入、输出、上下文和 token 的直观解释。
- 温度、最大输出长度、延迟和成本的基本概念。
- 为什么模型输出不是传统函数返回值。
- 如何保存一次调用的输入和输出，方便后续调试。

## 本章不要写什么

- 不要深入 Prompt 技巧。
- 不要引入 Agent。
- 不要把 API 参数讲成完整手册。

## 小白易卡点

- API Key 和环境变量配置失败。
- 以为模型输出应该像普通函数一样完全稳定。
- 不知道如何记录一次失败调用，导致后续无法调试。

## 建议示例

用一个最小脚本调用模型，让模型完成上一章定义的小任务。
