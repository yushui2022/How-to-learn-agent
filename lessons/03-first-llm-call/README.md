# 第 3 章：第一次 LLM 调用

> 状态：drafting

第 2 章已经把“AI 学习助手”压成了一个最小原型：

```text
用户输入学习问题 -> 系统输出解释、常见误区、下一步练习
```

这一章把它接到真正的模型调用上。

本章只做一件事：**跑通一次最小 LLM 调用，并把这次调用记录下来**。

本章回答三个问题：

- 一次 LLM 调用由哪些部分组成？
- 为什么模型输出不像普通函数返回值那样完全稳定？
- 第一次调用后应该记录什么，方便后续调 Prompt、评估和排错？

学完本章，你要留下三份项目资产：

- 一个最小可运行脚本：[minimal_llm_call.py](../../examples/minimal-llm-call/minimal_llm_call.py)
- 一份调用记录：[call-log-template.md](./call-log-template.md)
- 一份参数对比表：[parameter-comparison-template.md](./parameter-comparison-template.md)

## 先跑最小版本

从仓库根目录运行：

```powershell
python .\examples\minimal-llm-call\minimal_llm_call.py --dry-run
```

`--dry-run` 不会访问模型，它只打印即将发送给模型的请求。你应该先看懂请求结构，再填 API Key。

真正调用前，需要设置环境变量：

```powershell
$env:LLM_API_KEY="你的 API Key"
$env:LLM_MODEL="你账号可用的模型名"
$env:LLM_BASE_URL="https://api.openai.com/v1"
```

然后运行：

```powershell
python .\examples\minimal-llm-call\minimal_llm_call.py --question "什么是 RAG？"
```

不要把 API Key 写进代码，也不要提交 `.env` 文件。本仓库的 `.gitignore` 已经忽略 `.env` 和 `.env.*`。

## 一次 LLM 调用的 5 个部分

先不要急着学一堆参数。第一次调用只需要看懂 5 个部分。

| 部分 | 含义 | 本章示例 |
| --- | --- | --- |
| 模型 | 你要调用哪个模型 | 从 `LLM_MODEL` 读取 |
| 消息 | 你给模型的任务和用户问题 | system message + user message |
| 参数 | 控制输出风格和长度 | `temperature`、`max_tokens` |
| 输出 | 模型生成的文本 | 解释、常见误区、下一步练习 |
| 元数据 | 这次调用的成本、耗时、错误等信息 | usage、latency、error |

你可以把它想成这样：

```text
你的程序
  -> 组装请求：模型 + 消息 + 参数
  -> 发送给模型服务
  -> 收到输出文本和元数据
  -> 保存记录，供后续调试
```

## 模型不是普通函数

普通函数更像这样：

```text
add(1, 2) -> 3
```

只要代码不变，结果通常就不变。

LLM 调用不一样：

```text
answer("什么是 RAG？") -> 一段可能每次略有差异的回答
```

差异来自几个地方：

- 模型本身是生成式系统，不是查表。
- 同一个问题可以有多种合理表达。
- 参数会影响输出的稳定性、发散程度和长度。
- 上下文稍微变化，输出也可能变化。

所以 AI 项目不能只写“调用成功”。你还要记录输入、参数、输出和人工判断。

## 先理解 3 个参数

第一次调用只看 3 个参数就够了。

| 参数 | 作用 | 初学者怎么用 |
| --- | --- | --- |
| `model` | 选择模型 | 先用账号可用、成本可控的模型 |
| `temperature` | 控制输出发散程度 | 教学回答先用较低值，例如 `0.2` |
| `max_tokens` | 控制最大输出长度 | 先给足够空间，再根据结果缩小 |

不要在第一天纠结所有高级参数。先跑通，再观察。

## 为什么要保存调用记录

很多初学者第一次接 API，只关心屏幕上有没有输出。

这不够。

真实项目里，你迟早会遇到这些问题：

| 问题 | 如果没有记录会怎样 |
| --- | --- |
| 输出质量突然变差 | 不知道输入、模型、参数有没有变 |
| 调用失败 | 不知道是 Key、网络、额度还是请求格式问题 |
| 成本变高 | 不知道 token 用在哪里 |
| 后续调 Prompt | 没有旧结果可对比 |

所以从第一次调用开始，就要养成记录习惯。

最小记录包含：

- 时间。
- 输入问题。
- 模型名。
- 参数。
- 输出。
- 耗时。
- token 使用量，如果服务返回了 usage。
- 成功或失败原因。

本章用 [call-log-template.md](./call-log-template.md) 记录。

## 用第 2 章样例跑 3 次

拿第 2 章的输入输出样例，至少跑 3 次。

建议这样做：

| 次数 | 问题 | 参数 |
| --- | --- | --- |
| 1 | 什么是 RAG？ | `temperature=0.2` |
| 2 | 什么是 RAG？ | `temperature=0.8` |
| 3 | 帮我学会所有 AI | `temperature=0.2` |

观察三件事：

- 低温度输出是否更稳定。
- 高温度是否更容易发散。
- 面对过大的请求，模型有没有先澄清，而不是直接胡乱规划。

把结果写进 [parameter-comparison-template.md](./parameter-comparison-template.md)。

## 成熟项目观察：为什么会有 LiteLLM

本章的成熟项目主案例是 [LiteLLM](https://github.com/BerriAI/litellm)。

对应源码 Lab：

- [Lab 05：记忆、推理与模型服务专项](../../labs/05-memory-reasoning/README.md)

第一次调用可以直接写一个脚本。但真实项目不会永远停留在“裸调用”。

当项目变大后，你会遇到这些问题：

| 工程问题 | 为什么会出现 |
| --- | --- |
| 模型切换 | 不同模型价格、速度、质量不同 |
| 失败处理 | 模型服务可能超时、限流、返回错误 |
| 成本记录 | 每次调用都会消耗 token 和费用 |
| 调用日志 | 调试、评估、复盘都需要历史记录 |
| 统一接口 | 多个供应商的 API 形态不完全一致 |

LiteLLM 这类模型网关的价值，是把这些问题集中到一个模型服务层里处理。

但第二章和第三章的学习重点不是立刻引入模型网关。我们只迁移一个设计习惯：

```text
不要把模型调用散落在业务代码里。
先把一次调用包成一个清楚的函数，并记录输入、输出和错误。
```

本章示例脚本就做了这件事：

- `build_messages()` 负责组装消息。
- `call_chat_completion()` 负责发送请求。
- `main()` 负责读取参数、打印结果和记录耗时。

以后接 LiteLLM、模型网关、日志系统或评估系统时，就不会从一团散乱代码开始重构。

## 项目锚点

AI 学习助手在本章完成第一个可运行版本：

```text
输入：什么是 RAG？
输出：解释、常见误区、下一步练习
```

其他可选项目也只做一次最小调用：

| 项目 | 本章最小调用 |
| --- | --- |
| 研究写作 Agent | 输入研究主题，输出 5 个可搜索问题 |
| 客服工单 Agent | 输入工单文本，输出类型、紧急程度、建议处理人 |
| 代码仓库助手 | 输入 README 片段，输出项目用途和阅读入口 |

不要在本章引入 RAG、工具调用、记忆或 Agent loop。先确认模型能完成一个清楚的小任务。

## 动手任务

完成下面 4 件事：

1. 运行一次 dry-run，确认请求结构。
2. 配置环境变量，完成一次真实模型调用。
3. 用同一个问题跑两种 `temperature`，记录输出差异。
4. 把成功调用或失败调用写进 [call-log-template.md](./call-log-template.md)。

完成后，你应该能回答：

- 这次调用用了哪个模型？
- 发送给模型的消息是什么？
- 模型返回了什么？
- 调用耗时多久？
- 如果失败，失败发生在哪一层？

参考答案：

| 问题 | 参考判断 |
| --- | --- |
| 因为后续调试、对比、评估和成本分析都依赖输入、参数、输出和错误记录 |
| 不一定。高温度可能更发散，但教学类回答通常更需要稳定 |

## 本章小结

这一章你完成了从“需求文档”到“真实模型调用”的第一步。

你现在应该已经有：

- 一个能 dry-run 的最小调用脚本。
- 一次真实或可模拟的调用记录。
- 对 `model`、`temperature`、`max_tokens` 的基本直觉。
- 对模型输出不确定性的第一手观察。
