# 第 1 章：AI 项目到底在做什么

> 状态：drafting

假设你想做一个“AI 学习助手”。

一个很自然的想法是：

```text
我想做一个全自动学习 Agent。
它能规划学习路线、查资料、生成练习、批改答案、记住我的薄弱点，还能提醒我复习。
```

这个目标听起来很好，但它不适合作为第一版。

第一版更应该是：

```text
用户输入一个学习问题。
系统给出清晰解释，并给出下一步练习建议。
```

为什么要这样收缩？因为做 AI 项目的第一步，不是选框架，也不是写 Prompt，而是判断：

```text
这个需求到底属于哪种 AI 项目？
```

本章就解决这个问题。

## 你会学到什么

学完本章后，你应该能判断：

- 一个需求是否真的需要 AI。
- 一个 AI 需求适合 LLM 调用、RAG、工作流、工具调用还是 Agent。
- 为什么很多项目第一版不应该直接做成 Agent。
- OpenClaw 和 mem0 分别代表哪种 AI 项目形态。
- 你的练习项目第一版应该做多小。

## 本章产出

你需要留下三个产出：

- 一张 AI 项目类型判断表。
- 一个自己的项目地图。
- 一段说明：为什么你的项目第一版不应该直接做成 Agent。

可以使用 [project-map-template.md](./project-map-template.md) 完成本章产出。

## 先看一个容易犯错的版本

还是以“AI 学习助手”为例。

如果我们一开始就写：

```text
目标：做一个能自动学习规划、自动查资料、自动出题、自动批改、自动记忆、自动复习的 Agent。
```

这个目标会同时引入很多问题：

- 它需要长期记忆。
- 它需要工具调用。
- 它需要检索资料。
- 它需要规划任务。
- 它需要判断用户答案是否正确。
- 它需要记录学习进度。
- 它可能会给出错误学习建议。

这些能力后面都会学，但不应该在第一版同时出现。

第一版只做一件事：

```text
输入：我想理解一个概念。
输出：解释这个概念，指出常见误区，给出一个练习任务。
```

这时它还不是 Agent。它更像一个结构化 LLM 应用。

这个判断很重要。因为如果项目类型判断错了，后面技术路线也会错。

## AI 项目不是简单调用模型

很多入门教程会从“调用一次模型 API”开始，这没有问题。但一次模型调用不等于完整 AI 项目。

一次模型调用像这样：

```text
用户输入 -> 模型回答
```

一个 AI 项目更接近这样：

```text
用户任务
-> 应用程序理解任务
-> 组织上下文
-> 调用模型
-> 必要时检索资料或调用工具
-> 检查输出
-> 记录过程
-> 把结果交还用户
```

所以，在这门课里，我们先用这个定义：

```text
AI 项目是把模型能力放进真实任务流程里，并对输入、输出、上下文、工具、评估和风险做工程控制的系统。
```

这个定义里有几个关键词。

| 关键词 | 你需要关心什么 |
| --- | --- |
| 用户任务 | 用户到底想完成什么，而不是模型能表演什么 |
| 输入输出 | 用户给什么，系统返回什么，格式是否稳定 |
| 上下文 | 模型需要哪些背景信息才能答好 |
| 外部知识 | 是否需要课程资料、文档、数据库或网页 |
| 工具 | 是否需要搜索、读文件、查订单、运行代码 |
| 评估 | 怎么判断结果是有用、正确、稳定的 |
| 风险 | 模型错了会造成什么后果，哪些动作要限制 |

后面的章节会分别展开这些能力。本章只建立地图。

## AI 项目的类型地图

下面这张表是本章最重要的工具。

| 类型 | 适合什么问题 | 典型例子 | 第一版复杂度 |
| --- | --- | --- | --- |
| 普通程序 | 规则清楚、结果确定 | 表单校验、价格计算、权限判断 | 低 |
| 单次 LLM 调用 | 输入短、任务简单、允许一定不确定性 | 改写一句话、总结一段文本 | 低 |
| 结构化 LLM 调用 | 需要稳定字段输出 | 工单分类、信息抽取、生成 JSON | 中 |
| RAG 应用 | 需要外部资料支持回答 | 知识库问答、文档助手 | 中 |
| AI 工作流 | 多步骤但流程固定 | 先分类、再查询、再生成建议 | 中 |
| Tool Calling 应用 | 模型需要调用外部能力 | 查订单、查文件、运行测试 | 中高 |
| Agent | 步骤需要根据中间结果动态决定 | 研究任务、代码仓库分析、学习计划执行 | 高 |
| Multi-Agent | 任务天然需要多角色协作 | 研究员、写作者、审阅者协作 | 很高 |
| AI 基础设施 | 给其他 AI 应用提供能力 | 记忆服务、模型网关、评估平台 | 视范围而定 |

注意这张表不是排名。

不是越往下越高级，也不是越往下越好。正确的选择取决于任务。

## 小练习：先判断 5 个需求

先不要看后面的参考答案。试着判断下面这些需求分别属于哪类项目。

| 需求 | 你的判断 |
| --- | --- |
| 判断手机号格式是否正确 |  |
| 把一段会议记录总结成 5 个要点 |  |
| 根据公司知识库回答员工问题 |  |
| 查询订单状态后生成客服回复 |  |
| 围绕一个研究主题搜索资料、整理提纲、写初稿并审阅 |  |

参考判断：

| 需求 | 更合适的项目类型 | 原因 |
| --- | --- | --- |
| 判断手机号格式是否正确 | 普通程序 | 规则明确，不需要模型 |
| 把会议记录总结成 5 个要点 | 单次 LLM 调用 | 输入明确，任务短，不需要外部知识 |
| 根据公司知识库回答员工问题 | RAG 应用 | 需要使用外部资料，避免凭空回答 |
| 查询订单状态后生成客服回复 | Tool Calling 或 AI 工作流 | 需要查业务系统，再生成回复 |
| 搜索资料、整理提纲、写初稿并审阅 | Agent 或 Multi-Agent | 任务长，步骤会变化，可能需要多角色协作 |

判断时不要追求术语漂亮。你只需要问：这个任务需要什么能力，最小可行版本是什么。

## 怎么判断是否需要 AI

先问一个问题：

```text
这个任务用普通程序能不能稳定解决？
```

如果能，就不要强行用 AI。

比如：

- 判断手机号格式。
- 计算订单总价。
- 判断用户权限。
- 根据固定状态流转工单。

这些任务用普通程序更便宜、更稳定、更可解释。

AI 更适合下面这些任务：

- 输入是自然语言。
- 用户表达方式很多变。
- 需要总结、分类、抽取、改写或生成。
- 需要结合大量文本资料回答。
- 很难写出完整规则。

但即使需要 AI，也不代表需要 Agent。

## 怎么判断是否需要 Agent

可以用这组问题判断。

| 判断问题 | 如果答案是“是” | 更可能选择 |
| --- | --- | --- |
| 只需要生成一次回答吗？ | 是 | 单次 LLM 调用 |
| 输出字段需要稳定吗？ | 是 | 结构化输出 |
| 需要查外部资料吗？ | 是 | RAG |
| 步骤固定吗？ | 是 | AI 工作流 |
| 需要调用外部工具吗？ | 是 | Tool Calling 应用 |
| 下一步需要根据中间结果动态决定吗？ | 是 | Agent |
| 任务很长，需要保存进度吗？ | 是 | Agent + State |
| 需要多个角色互相审阅吗？ | 是 | Multi-Agent |

Agent 的核心不是“会调用工具”，而是：

```text
系统能根据目标、上下文和反馈，动态决定下一步行动。
```

这也意味着 Agent 的失败成本更高。它可能：

- 调错工具。
- 重复执行同一步。
- 把临时信息当成事实。
- 在错误方向上越走越远。
- 消耗更多 token 和时间。
- 做出需要人工确认的高风险动作。

所以本课程会先讲 LLM、Prompt、结构化输出、工作流、RAG、Tool Calling，再进入 Agent。

## 回到 AI 学习助手

现在我们重新判断“AI 学习助手”。

第一版需求：

```text
用户输入一个学习问题，系统返回清晰解释、常见误区和下一步练习。
```

这个需求需要 AI，因为：

- 用户输入是自然语言。
- 解释和练习建议很难用固定规则写完。
- 输出需要适应不同学习问题。

但第一版不需要 Agent，因为：

- 它不需要动态规划多步任务。
- 它不需要长期保存状态。
- 它不需要调用外部工具。
- 它不需要自主决定下一步行动。

所以第一版可以判断为：

```text
结构化 LLM 应用
```

后续再逐步升级：

| 阶段 | 增加的能力 | 对应章节 |
| --- | --- | --- |
| 第一版 | 回答学习问题，输出解释和练习 | 第 03-05 章 |
| 第二版 | 按固定流程生成解释、误区和练习 | 第 06 章 |
| 第三版 | 接入课程资料和个人笔记 | 第 07-08 章 |
| 第四版 | 调用工具生成练习、保存学习记录 | 第 09 章 |
| 第五版 | 根据学习目标循环执行任务 | 第 10-12 章 |
| 第六版 | 记住学习目标、进度和薄弱点 | 第 13 章 |
| 第七版 | 增加评估、日志、安全和上线 | 第 15-18 章 |

这就是本章的核心方法：

```text
先判断项目形态，再选择技术路线。
```

## 成熟项目讲解：OpenClaw 和 mem0

本章不读源码，只观察成熟项目的定位。

- 主案例：OpenClaw、mem0。
- 讲解切口：产品型 AI 助手和基础设施型记忆服务分别解决什么问题。
- 对应源码 Lab：[Lab 01：通用核心框架](../../labs/01-core-frameworks/README.md)、[Lab 05：记忆、推理与模型服务专项](../../labs/05-memory-reasoning/README.md)。
- 迁移到项目：帮助你判断自己的项目是应用、工具、平台还是底层组件。

OpenClaw 更像一个面向用户的个人 AI 助手产品。观察它时，不要先看复杂实现，而是先看：

- 它面向什么用户？
- 它提供什么入口？
- 它把哪些能力包装成了产品？
- 它为什么不只是一次模型调用？

mem0 更像一个面向开发者的记忆基础设施。观察它时，重点看：

- 它给其他 AI 应用提供什么能力？
- 它为什么不直接做成一个聊天产品？
- 如果我们做 AI 学习助手，未来可能借鉴它的哪一块？

这两个项目放在一起看，能帮你理解：

```text
AI 项目既可以是应用层产品，也可以是底层能力组件。
```

对应到“AI 学习助手”：

- 如果我们做给学习者直接使用，它是应用层产品。
- 如果我们只做一个“学习记忆服务”，供其他学习应用调用，它就是基础设施组件。

本课程默认做前者：先做一个用户能使用的 AI 学习助手。

## 开源案例观察

对比 OpenClaw 和 mem0：

| 观察点 | OpenClaw | mem0 |
| --- | --- | --- |
| 面向谁 | 终端用户 / 个人助手使用者 | 开发者 / AI 应用构建者 |
| 主要价值 | 帮用户完成任务 | 给 AI 应用提供长期记忆 |
| 更像什么 | 产品型 AI 助手 | 基础设施组件 |
| 本章学习点 | 看 AI 产品边界 | 看 AI 能力组件边界 |

本章不要求读者读源码，只观察 README、功能定位和项目边界。

```text

mem0 更像什么项目？为什么？
这对我的 AI 学习助手有什么启发？
```

## 项目锚点

贯穿项目“AI 学习助手”在本章只做项目类型判断。

它一开始应该是：

```text
结构化 LLM 应用
```

不是：

```text
复杂自主 Agent
```

本章结束时，你要为自己的项目写出：

- 目标用户。
- 核心任务。
- 第一版输入。
- 第一版输出。
- 第一版项目类型。
- 暂时不做什么。
- 后续如何逐步升级到 Agent。

## 本章边界

本章不展开这些内容：

- Prompt 怎么写。
- RAG 怎么实现。
- Tool Calling 怎么定义工具。
- Agent loop 怎么运行。
- LangGraph、OpenHands、CrewAI 这类框架怎么用。

这些内容后面都会讲。本章只做一件事：建立项目地图。

## 小白易卡点

- 以为调用模型就等于完成 AI 项目。
- 以为所有 AI 应用都应该做成 Agent。
- 不知道 AI 输出的不确定性会怎样影响工程设计。
- 不知道产品型 AI 项目和基础设施型 AI 项目的区别。

记住这句话：

```text
先判断项目形态，再选择技术路线。
```
