# 第 1 章：AI 项目到底在做什么

> 状态：drafting

很多人第一次做 AI 项目时，会把问题想得太简单：接一个模型 API，写几句 Prompt，然后就以为项目完成了。也有人会走到另一个极端：还没搞清楚需求，就想直接做一个全自动 Agent。

这两种想法都会让项目失控。

本章先不讲复杂框架，也不讲源码实现。我们先建立一张地图：AI 项目常见有哪些形态，它们分别解决什么问题，什么时候需要 LLM，什么时候需要 RAG，什么时候需要工作流，什么时候才值得进入 Agent。

## 本章定位

本章帮助读者建立 AI 项目的基本地图。

读者要先理解一件事：

```text
AI 项目不是“调用模型”这么简单，也不是所有 AI 项目都应该做成 Agent。
```

一个靠谱的 AI 项目至少要回答：

- 用户是谁？
- 用户的问题是什么？
- 输入和输出是什么？
- 模型在系统里负责哪一部分？
- 需要不需要外部知识？
- 需要不需要调用工具？
- 失败成本能不能接受？
- 如何判断结果是好的？

如果这些问题答不清楚，后面讲 Prompt、RAG、Tool Calling、Agent 都会变成堆技术名词。

## 先用一句话定义 AI 项目

在这门课里，我们先用一个工程化定义：

```text
AI 项目是把模型能力放进一个真实任务流程里，并对输入、输出、上下文、工具、评估和风险做工程控制的系统。
```

这个定义里有几个关键词。

| 关键词 | 含义 |
| --- | --- |
| 模型能力 | LLM 可以理解、生成、总结、分类、推理、改写、抽取信息 |
| 真实任务流程 | 用户不是为了看模型表演，而是要完成一个具体任务 |
| 输入输出 | 系统必须知道用户给什么、系统返回什么 |
| 上下文 | 模型需要哪些背景信息才能回答好 |
| 工具 | 模型是否需要调用搜索、数据库、文件、浏览器或业务 API |
| 评估 | 如何判断输出是否有用、正确、稳定 |
| 风险 | 模型错了会带来什么后果，哪些动作必须限制 |

所以，AI 项目不是：

```text
用户输入 -> 模型回答
```

更接近：

```text
用户任务
-> 应用程序理解任务
-> 组织上下文
-> 调用模型
-> 必要时检索资料或调用工具
-> 检查输出
-> 记录过程
-> 把结果交还用户
```

## AI 项目的常见形态

下面这张表是本章最重要的地图。

| 类型 | 适合什么问题 | 典型例子 | 是否需要 Agent |
| --- | --- | --- | --- |
| 普通程序 | 规则清楚、结果确定 | 表单校验、价格计算、权限判断 | 不需要 |
| 单次 LLM 调用 | 输入短、任务简单、允许一定不确定性 | 改写一句话、总结一段文本 | 不需要 |
| 结构化 LLM 调用 | 需要稳定字段输出 | 工单分类、信息抽取、生成 JSON | 不需要 |
| RAG 应用 | 需要外部资料支持回答 | 知识库问答、文档助手 | 通常不需要 |
| AI 工作流 | 多步骤但流程固定 | 先分类、再查询、再生成建议 | 通常不需要 |
| Tool Calling 应用 | 模型需要调用外部能力 | 查订单、查文件、运行测试 | 不一定需要 |
| Agent | 任务目标明确，但步骤需要动态决定 | 研究任务、代码仓库分析、学习计划执行 | 可能需要 |
| Multi-Agent | 任务天然需要多角色协作 | 研究员、写作者、审阅者协作 | 谨慎使用 |
| AI 基础设施 | 给其他 AI 应用提供能力 | 记忆服务、模型网关、评估平台 | 本身未必是 Agent |

一个常见误区是：只要模型能调用工具，就叫 Agent。

这不准确。工具调用只是 Agent 的一个能力。真正进入 Agent，通常意味着系统要根据目标、上下文和反馈动态决定下一步，而不是只执行固定流程。

## 判断一个需求是否需要 AI

先问一个问题：

```text
这个任务用普通程序能不能稳定解决？
```

如果答案是能，就不要强行用 AI。

比如：

- 判断手机号格式是否正确。
- 计算订单总价。
- 判断用户是否有某个权限。
- 根据状态机流转工单状态。

这些任务规则明确，用普通程序更便宜、更稳定、更可解释。

AI 更适合下面这些任务：

- 输入是自然语言，不容易写完整规则。
- 用户表达方式变化很大。
- 需要总结、改写、分类、抽取、生成。
- 需要结合大量文本资料回答。
- 任务过程里有不确定性，需要模型做判断。

但即使需要 AI，也不代表一开始就需要 Agent。

## 判断一个需求是否需要 Agent

可以用这张判断表。

| 问题 | 如果答案是“是” | 更可能选择 |
| --- | --- | --- |
| 只需要生成一次回答吗？ | 是 | 单次 LLM 调用 |
| 输出字段需要稳定吗？ | 是 | 结构化输出 |
| 需要查外部资料吗？ | 是 | RAG |
| 步骤固定吗？ | 是 | AI 工作流 |
| 需要调用外部工具吗？ | 是 | Tool Calling 应用 |
| 下一步需要根据中间结果动态决定吗？ | 是 | Agent |
| 任务很长，需要保存进度吗？ | 是 | Agent + State |
| 需要多个角色互相审阅吗？ | 是 | Multi-Agent |

Agent 不是越早用越好。Agent 的能力越强，失败成本也越高。

它可能会：

- 调错工具。
- 重复执行同一步。
- 把临时信息当成事实。
- 在错误方向上越走越远。
- 消耗更多 token 和时间。
- 做出需要人工确认的高风险动作。

所以这门课会先讲 LLM、Prompt、结构化输出、工作流、RAG、Tool Calling，再进入 Agent。

## 用“AI 学习助手”做一次判断

我们的贯穿项目是：

```text
AI 学习助手
```

一个冲动的版本可能会这样设计：

```text
我要做一个全自动学习 Agent，它能规划学习路径、查资料、生成练习、批改答案、长期记忆、自动复习、主动提醒。
```

这听起来很完整，但不适合作为第一版。

第一版应该更小：

```text
用户输入一个学习问题，系统返回清晰解释，并给出下一步练习建议。
```

这个第一版更像：

```text
结构化 LLM 调用
```

后续再逐步升级：

| 阶段 | 能力 | 对应章节 |
| --- | --- | --- |
| 第一版 | 回答学习问题 | 第 03-05 章 |
| 第二版 | 按固定流程生成解释和练习 | 第 06 章 |
| 第三版 | 接入课程资料和笔记 | 第 07-08 章 |
| 第四版 | 调用工具生成练习、保存记录 | 第 09 章 |
| 第五版 | 根据学习目标循环执行任务 | 第 10-12 章 |
| 第六版 | 记住学习目标和薄弱点 | 第 13 章 |
| 第七版 | 增加评估、日志、安全和上线 | 第 15-18 章 |

这就是本章要建立的判断：先确定项目类型，再决定技术路径。

## 成熟项目讲解

- 主案例：OpenClaw、mem0。
- 讲解切口：产品型 AI 助手和基础设施型记忆服务分别解决什么问题。
- 对应源码 Lab：[Lab 01：通用核心框架](../../labs/01-core-frameworks/README.md)、[Lab 05：记忆、推理与模型服务专项](../../labs/05-memory-reasoning/README.md)。
- 迁移到项目：帮助读者判断自己的项目是应用、工具、平台还是底层组件。

OpenClaw 更像一个面向用户的个人 AI 助手产品。观察它时，不要先看复杂实现，而是先看它试图给用户提供什么入口、什么能力、什么使用方式。

mem0 更像一个面向开发者的记忆基础设施。它不是直接替用户完成完整任务，而是给其他 AI 应用提供长期记忆能力。

这两个项目放在一起看，能帮读者理解：

```text
AI 项目既可以是应用层产品，也可以是底层能力组件。
```

对应到“AI 学习助手”：

- 如果我们做给学习者直接使用，它是应用层产品。
- 如果我们只做一个“学习记忆服务”，供其他学习应用调用，它就是基础设施组件。

本课程默认做前者：先做一个用户能使用的 AI 学习助手。

## 项目锚点

贯穿项目“AI 学习助手”在本章只做项目类型判断。

它一开始应该是：

```text
结构化 LLM 应用
```

不是：

```text
复杂自主 Agent
```

本章结束时，读者要为自己的项目写出：

- 目标用户。
- 核心任务。
- 第一版输入。
- 第一版输出。
- 第一版项目类型。
- 暂时不做什么。
- 后续如何逐步升级到 Agent。

## 本章不要写什么

- 不要深入 Prompt、RAG、Tool Calling 或 Agent 实现。
- 不要一开始就介绍复杂框架。
- 不要把所有 AI 项目都叫 Agent。
- 不要要求读者现在做完整架构设计。

## 小白易卡点

- 以为调用模型就等于完成 AI 项目。
- 以为所有 AI 应用都应该做成 Agent。
- 不知道 AI 输出的不确定性会怎样影响工程设计。
- 不知道产品型 AI 项目和基础设施型 AI 项目的区别。

本章的关键提醒是：

```text
先判断项目形态，再选择技术路线。
```

## 建议示例

本章可以配一个“需求判断”示例。

示例：

```text
需求：用户上传一份课程笔记，系统回答和笔记相关的问题。
```

判断：

```text
这不是普通 LLM 调用，因为模型需要使用外部笔记。
这也不一定需要 Agent，因为流程可以固定为：上传 -> 切分 -> 检索 -> 回答。
所以第一版更适合做 RAG 应用。
```

## 建议图解

本章适合画一张 AI 项目类型地图：

```text
普通程序
  -> 单次 LLM 调用
  -> 结构化 LLM 调用
  -> RAG
  -> AI 工作流
  -> Tool Calling
  -> Agent
  -> Multi-Agent
```

图解要表达能力逐步增强，复杂度和风险也逐步增加。
